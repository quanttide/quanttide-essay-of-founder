# 设计操作系统：模型做选择，代码做校验

本文讨论 AI 生成界面时的架构分工。它不介绍某个具体界面的设计，只回答三个问题：为什么模型直接生成像素或组件树的方式缺一个设计操作系统，这个系统由什么组成，以及确定性校验层能承担多少规则。相关实践尚在早期，故本文停留在初稿。

## 问题：只有风格碎片

让模型直接吐像素或 Widget 树，结果往往「看起来像设计过」，细看经不起推敲：首屏塞满元素，间距随手取值，字号层级互相打架。问题不在于模型不会画，而在于系统里没有任何一处替它守住设计规则。

风格碎片可以逐个补：提示词里加一句「保持简洁」，示例里多放一张好图。但碎片补不成系统，因为没有任何环节会拒绝一个违规的结果。生成端的引导只影响倾向，不影响结果能不能进来；参考与约束不是程度差别，而是机制差别，见[智能体架子](../agent/agent-harness.md)。

缺的是一部设计操作系统：把设计规则从提示与示例里拿出来，变成系统中真实存在、会拒绝输入的那一层。

## 分工：模型做选择，代码做校验

分工只有一句话：模型负责意图与取舍，确定性系统负责落地与校验。不让模型直接吐像素或 Widget 树，让它在一个强约束的中间层里做选择。

这个分工的理由是两种能力的性质不同。模型擅长判断：从一句需求里读出任务类型、定出唯一视觉锚点、排出信息层级——这些是取舍，没有唯一解，正需要模型。代码擅长守规：数元素个数、量间距取值、查对比度——这些有唯一解，而且不能错。把守规交给模型，等于让一个会犯错的人扮演不会犯错的角色；把取舍交给代码，等于让一套规则去猜没说出口的意图。两边都放错了。

## 中间层：一个设计 DSL

模型与校验层之间需要一个中间表示。它是一份结构化描述，只记录设计意图，不含任何像素坐标：

```json
{
  "intent": "quick_scan",
  "primary": "current_price",
  "hierarchy": ["price", "trend_24h", "volume", "detail_tabs"],
  "density": "compact",
  "tone": "data_cool",
  "max_elements": 7,
  "avoid": ["gradient_card", "emoji_icon", "redundant_label"]
}
```

`intent` 是任务类型：扫读、对比、沉浸式阅读、录入。`primary` 是唯一视觉锚点，`hierarchy` 排信息层级，`density` 与 `tone` 定密度与调性，`max_elements` 是硬预算，`avoid` 是显式排除项。

DSL 的价值在于把「设计」压缩成一组可校验的选择。模型的自由度只在取值范围内；越界不是扣分，是直接拒绝。这样模型犯错的代价被固定为「重来一次」，而不是「带着违规进入渲染」。

## 校验层：六条硬规则

DSL 进来后，由一段不会犯错的代码去算。这一步完全不用模型。

1. 信息预算：7±2 原则，首屏元素数超了直接报错回退，不重试、不降级。
2. 栅格与间距：8pt 基准，间距只许取 [4, 8, 12, 16, 24, 40] 这个离散集合，13、17 这类野值拒绝。
3. 字号阶梯：定义一条 modular scale（如 1.25 倍率），相邻层级差不够一个台阶的拒绝。
4. 视觉重量守恒：页面只允许一个 weight 为 1.0 的锚点，其余不超过 0.6，杜绝五个标题抢眼球。
5. 可访问性：对比度达 WCAG AA，触控区不小于 44pt，禁用纯色彩编码。
6. 布局有效性：用 Flutter 的 TextPainter / CustomPainter 预演一次，溢出即重排，不把溢出留给运行时。

六条的共同点是都返回真假，不返回分数。分数意味着可以商量，真假意味着没有余地。校验层不改善结果，只决定结果进不进来；改善发生在模型重新选择的下一轮。

## 为什么这一步不用模型

校验层不用模型，理由有三。快：六条规则是常数级检查，毫秒内完成，不增加生成延迟。可验证：每条规则输入输出明确，可以单元测试，可以对历史界面回归。可信任：规则的输出只取决于输入，本身不会犯错；用模型校验模型，校验端自己的波动会混进结论。

模型在系统里的位置因此固定下来：它只在 DSL 的取值空间里做选择，做错会被拒绝重来，错误被限制在生成端，不会累积到渲染端。

## 边界与待定

三件事还没定。DSL 的取值空间怎么维护：硬编码进校验器，还是做成可配置的主题文件，等第二、三个界面类型出现再决定。校验失败后的重试策略：把拒绝理由回传给模型重新选择，还是回退到上一版界面，需要实验对比。六条之外还有哪些规则能进硬校验：颜色语义、动效强度是否可判，判不了的留在人判，不硬塞进代码。

## 初步结论

设计操作系统由三部分组成：一份记录意图的 DSL，一套返回真假的校验规则，一个只在取值空间内做选择的模型。模型把需求翻译成意图，代码让违规的意图无法变成界面。

这不是用代码取代设计，而是把设计里可计算的部分真正交给计算：预算、栅格、阶梯、重量、可访问性，从来都是可计算的；不可计算的是取舍，取舍留给模型。计算设计真正发力的地方，就在这条分界线上。
