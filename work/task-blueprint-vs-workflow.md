# 任务蓝图与工作流：两种定义的终点

本文是初步工作论文，比较同一项目里的两份过程定义：文件级的任务蓝图与领域级的工作流。两者都写「一串有序的步骤」，表面差别像抽象层次，实质差别是定义在哪里结束。本文先逐项对照，再给出一个阶段性判断：以任务蓝图为一等公民，工作流降为可选投影。

## 两种文本

任务蓝图是一份 Markdown 文档里的 `yaml work` 块。它写输入、前置、步骤、验收标准、偏差与边界，目标是一件事可以被重复执行；把散文删掉，执行器仍能读懂；把执行器删掉，散文里的命令仍能让人把事做完。

工作流是工作区里的一个领域实体。它有派生的 UUID、区内唯一的名字、一句描述与一组步骤；步骤只有 `id`、`name`、`description` 三枚。工作流被工作任务引用，工作任务用只增不改的流水逐站对账。它的目标不是自己跑起来，而是被引用、被记账、被审计。

两者共享两条骨架：先声明后执行，验收标准挂在步骤上。差别不在骨架，而在骨架之外还写什么。

## 完备性的方向相反

任务蓝图的完备性是向外扩的。它一直写到「这件事可以重跑」为止：输入要有类型与默认值，前置要有不成立时的处置，步骤要有能力名与参数，失败要有偏差表，边界要写「不做」。它假设执行者可能是一个脚本、一个 AI，或一个照着散文敲命令的人，所以任何一处留白都会在执行时变成猜测。

工作流的完备性是向内收的。它只写到「这一站可以被指认、可以被对账」为止：步骤一句 `description` 写做什么，验收标准只给 `executor` 与 `description`，`rule` 的判法明确下放给平台。它不假设自己会被直接执行，而假设有一个平台实现者把规则引擎、智能体或人接上去。

于是两种定义的世界不同：任务是封闭的执行世界，定义不完整就跑不起来；工作流是封闭的 schema、开放的执行语义，定义完整到可以引用即止。用一句话说，任务蓝图回答「怎么再做一遍」，工作流回答「这一站在系统里是谁」。

## 身份与变更

任务蓝图的身份在文件系统里：`work` 名等于文件名，`版本` 是整数，历史交给 git。改步骤就改文件、版本加一；需要旧版就翻提交记录。它不另立登记处，也不要求引用方持有凭证。

工作流的身份在登记处：`id` 按「工作区 id + 工作流名」派生，名字在区内唯一，被工作任务引用后定义冻结；要改站名、删步骤、调次序，须另立一条工作流，旧定义原样保留。工作步骤的规格里有一句话把这条纪律说得很准：定义不是账本，可以靠位置；账本不是定义，必须靠凭证。

这不是实现细节，而是两种时间观。工作流假设定义一旦被引用就该稳定，稳定才能对账；任务蓝图假设定义还在被摸索，能改才能继续逼近正确。对探索性的工作，前者的冻结是税，后者的版本化是路。

## 验收标准的位置

任务蓝图把验收标准写在定义里：四种固定句式，失败即该步失败，后续不执行，偏差表按现象给处置。它不只说「谁判」，还说「怎么判」「判不过怎么办」。这是它能被 mock 执行器跑通的原因——换实现不换流程，验收标准仍然成立。

工作流把验收标准写成两枚字段：`executor` 答谁判，`description` 答判什么。`rule` 的判法由平台定义，规格自身不给形状。它关心的是放行权归谁，而不是判断长什么样。于是工作流可以管住「谁签字」，却管不住「签字的依据是不是可复现」。

两种写法没有对错，只有先后。验收标准的形状一旦稳定，就应该写进定义；放行权一旦涉及多人，就应该独立成层。任务蓝图先做前者，工作流先做后者。

## 两种读者，两种语言

任务蓝图是写作指南：字段表、示例、自检、必填与不允许。它用祈使句，读者是写流程的人和执行器。它甚至规定散文与块各写什么，因为「写对」本身就是规格的一部分。

工作流是本体规格：字段、关联、约束、领域事件、API 端点。它用陈述句，读者是平台实现者与审计者。它不教你怎么写一条好工作流，只定义什么算一条工作流。

这也是「定义风格」最直观的差别：一份在教人写文档，一份在定义一种存在。

## 阶段性判断

在当前阶段，我倾向于淘汰工作流，以任务蓝图为真源。理由不是工作流错了，而是它优化的三件事——多任务复用、跨平台一致、可审计——目前都不是主要矛盾。主要矛盾是：一件事能不能被写清楚、被 AI 或脚本重复做出来、换一个实现要不要改定义。

工作流的「引用即冻结」与这个阶段冲突。活还在探索，定义需要边跑边改；先冻结再干活，等于把学习成本提前支付。工作流的不自足也造成两处真源：步骤只有一句描述，真正的做法在散文与能力实现里，判断又在平台里；任务蓝图则把做法、验收标准、失败处置收在一处。

淘汰的具体含义是降级，而不是否认：任务蓝图是唯一真源；工作流、工作任务、工作记录如果将来需要，只能由蓝图派生，作为治理投影存在，不得反向成为定义的上游。这样既保留执行语义的完整，也给治理留了后门。产物与契约的分工另文讨论，见[产物契约](./artifact-contract.md)。

## 代价与待解

第一条代价是运行中的漂移。蓝图可以原地改，任务跑到一半定义变了，重跑与对账就对不上。需要一条纪律：每次运行锁定蓝图版本或哈希，快照随运行记录保存。

第二条是复用失去显式模型。工作流天然服务多个任务；蓝图更接近一个一个任务。跨任务复用只能靠目录、命名与参数化约定，容易长成复制粘贴。

第三条是治理后置的账。多人协作、合规审计、跨系统事件最终仍需要记录与凭证；可以后补，但不能假装不需要。后补的前提是蓝图从第一天就留下可派生治理信息的字段，而不是等需要时再从散文里猜。

## 结论

两种定义的终点不同：任务蓝图停在「可以重跑」，工作流停在「可以被引用和对账」。前者把执行语义写进定义，后者把身份与责任写进定义。当前选择任务蓝图，是选择让执行先行、治理后置；这不是终局判断，而是阶段判断——当多平台一致与审计重新成为瓶颈，工作流式的投影还会回来，但那时它应该是蓝图的派生，而不是蓝图的替代。
